# FluxHelper 2.3.4 — вхід через Google на телефоні. Повна інструкція

## 1. Що насправді зламано (результат розслідування)

Я декомпілював твій релізний `FluxHelper_v2.3.3.apk` і знайшов **справжню причину** всіх
проблем — вона не в консолі Google і не в схемі:

**Головний баг (Java):** у `MainActivity.java` методи `oauthStart()`, `oauthLoopback()`,
`authStart()` позначені `@JavascriptInterface`, але в WebView зареєстровано **тільки**
внутрішній об'єкт `Host`:

```java
this.wv.addJavascriptInterface(new Host(), "AndroidHost");
```

Android віддає в JS лише методи **того об'єкта, що зареєстрований**. Методи самої
активності в мост не потрапляють. Тому з HTML-інтерфейсу виклики
`AndroidHost.oauthStart()` (системний вхід!) і `AndroidHost.oauthLoopback()` кидали
`TypeError`, помилка мовчки ковталася `try/catch`, і залишався останній шлях —
`AndroidHost.open()` з адресою `http://127.0.0.1:8765/...`, яку ніхто не слухав.
Звідси і «localhost вбито», і `ERR_CONNECTION_REFUSED`, і «вхід не працює взагалі».

**Друге відкриття (дослідження в інтернеті):** твою ідею зі схемою
`kyiv1.blazix1.blazix1://oauth` Google **не дозволить реалізувати в принципі**:

| Факт | Джерело |
|---|---|
| «Custom URI schemes are no longer supported on Android and Chrome apps» — довільні кастомні схеми для Android заборонено | Google, офіційна документація OAuth 2.0 для native-app (developers.google.com/identity/protocols/oauth2/native-app) |
| Жовтень 2023: «нові Android-застосунки більше не зможуть використовувати Custom URI schemes для авторизації» | Google Developers Blog, «Improving user safety in OAuth flows» |
| Кастомні схеми не приймаються для типу «Веб-застосунок» («Custom scheme URIs are not allowed for WEB client type») | issues відомих OAuth-плагінів, stack overflow |
| «Invalid Origin: URIs must not contain a path or end with "/"» — це помилка поля **Authorized JavaScript origins**, куди взагалі не треба нічого писати в нашому випадку. Redirect-URL пишуть в іншому полі — **Authorized redirect URIs** — і там шляхи дозволені | логіка консоли Google Cloud |
| Для типу «Настільний застосунок» консоль не дає додавати redirect-URI — і це НОРМАЛЬНО: loopback (`http://127.0.0.1`) для нього дозволений автоматично, нічого реєструвати не треба | та ж документація |

Тобто: у консолі ти робив усе правильно наскільки це взагалі можливо — просто
додати «свою» схему куди-небудь **неможливо за дизайном Google**. Обхідний шлях
існує і саме його ти вгадав: **своя сторінка входу на Cloudflare Worker**.

**Третє відкриття (2.3.0):** тодішня помилка «Custom URI scheme is not enabled»
мала конкретну причину — у Google Cloud Console в **Android-клієнта** має бути
правильний **package name** та **SHA-1**. Реальний пакет твого APK —
`com.fluxhelper.app` (я витягнув його з манифеста релізного APK). Якщо там
вказано `Kyiv1.Blazix1.Blazix1` (так ти називав його в минулому повідомленні) —
Google відхиляє схему саме з цією помилкою.

## 2. Як тепер улаштований вхід (2.3.4)

Порядок шляхів на телефоні (перший робочий виграє):

```
[Кнопка «Увійти через Google»]
  └─ 1. Системний акаунт пристрою (AccountManager) — без браузера
        │  працює після Java-патчу (метод oauthStart тепер доступний мосту)
        ▼ якщо не вдалося
[Кнопка «Увійти через браузер»]
  └─ 2a. МІСТ — твій Cloudflare Worker (рекомендовано, гарантовано працює)
        │  браузер → worker/login → Google → worker/callback →
        │  → зашифрований одноразовий код FH1.… → повернення в застосунок
        └─ 2b. ПРЯМИЙ — Android-клієнт + його генерована схема + PKCE
        │  (працює, якщо в консолі правильний package + SHA-1)
        └─ 2c. стара loopback-петля (як на ПК) — останній шанс
```

ПК **не змінено взагалі**: той самий настільний клієнт, той самий loopback,
той самий секрет — як у версіях, де «все працювало».

## 3. Крок 1 — виправити Java (5 хвилин)

Файл **`android/MainActivity-patch.java`** містить готові шматки. У своєму
`MainActivity.java`:

1. **Секція A** — чотири методи-проксії додай **всередину класу `Host`**
   (перед його закриваючою дужкою). Це і є фікс головного бага.
2. **Секція B** — методи `pkce()` і `b64url()` додай у **MainActivity**
   (поруч з `oauthStart()`, НЕ всередині Host).
3. Секція C — чекліст того, що змінювати не треба.

## 4. Крок 2 — замінити index.html (2 хвилини)

Файл **`android/index.html`** — це твій релізний інтерфейс 2.3.3 з уже
вбудованими змінами (я брав оригінал саме з випущеного APK):

- обмін коду трьома шляхами: міст (FH1.→worker/token), пряма схема
  (Android-клієнт + PKCE, без секрету), ПК/loopback (як було, з секретом);
- refresh-токен оновлюється тим шляхом, яким прийшов вхід (`USER.via`);
- кнопка «Увійти через браузер» веде: міст → пряма схема → loopback;
- дистанційна конфігурація приймає нове поле `oauth.worker` (URL мосту);
- ПК-вхід (`fh:oauth`, loopback 127.0.0.1:8765, десктопний клієнт) — недоторканний.

Просто заміни ним свій `assets/www/index.html` (або повтори зміни руками,
якщо твій локальний файл відрізняється — усі правки позначені коментарями `2.3.4`).

**Після деплою воркера впиши його URL у константу** (рядок ~64):
```js
const FH_WORKER_DEFAULT = 'https://fluxhelper-auth.ТВІЙ-СУБДОМЕН.workers.dev';
```

## 5. Крок 3 — виправити клієнти в Google Cloud Console

Відкрий console.cloud.google.com → APIs & Services → Credentials (проєкт `fluxhelper-1`).

### 5.1. Android-клієнт (668834523935-14h6abj7232pjnr1imhcdvihm3nthfv2)
- Відкрий його. Перевір два поля:
  - **Package name** = `com.fluxhelper.app`  ← саме так; якщо стоїть
    `Kyiv1.Blazix1.Blazix1` — виправ, це ламало 2.3.0;
  - **SHA-1** = `68:71:F0:D5:FA:DA:C1:09:33:49:20:95:BD:32:2D:4B:F8:1A:83:73`
- Нічого більше. Redirect URI тут НЕ потрібні — схему
  `com.googleusercontent.apps.668834523935-14h6abj…:/oauth2redirect` Google
  генерує і дозволяє сам, вона вже в манифесті APK.

### 5.2. Новий клієнт для мосту — тип «Веб-застосунок»
- Create Credentials → OAuth client ID → **Web application**.
- **Authorized JavaScript origins: залиш ПОРОЖНІМ.** (Твоя помилка
  «Invalid Origin: URIs must not contain a path» була саме тут — у це поле
  path писати не можна, але нам воно й не потрібне.)
- **Authorized redirect URIs** — додай ОДИН:
  ```
  https://fluxhelper-auth.ТВІЙ-СУБДОМЕН.workers.dev/callback
  ```
  (підставиш після деплою воркера з кроку 4; шляхи тут дозволені)
- Скопіюй **Client ID** і **Client secret** — вони йдуть у змінні воркера.

### 5.3. Настільний клієнт (668834523935-t8gqql…)
**Не чіпай взагалі нічого.** Те, що в нього «не можна додати посилання» —
нормально: loopback для нього дозволений автоматично.

### 5.4. OAuth consent screen
- Якщо застосунок у режимі **Testing** — refresh-токени протухають через 7 днів.
- Натисни **Publish app** (scope openid/email/profile — базові, перевірка
  Google не потрібна, застосунок стане «In production»).

## 6. Крок 4 — задеплоїти Worker на Cloudflare (10 хвилин)

Твій файл: **`worker/worker.js`**. Cloudflare-акаунт у тебе вже є (D1).

1. dash.cloudflare.com → **Workers & Pages** → **Create** → **Create Worker**.
2. Назва: `fluxhelper-auth` → Deploy → **Edit code**.
3. Стриши вміст `worker/worker.js` у редактор (повністю заміни шаблон) → **Deploy**.
4. Worker → **Settings** → **Variables and Secrets** → додай:
   | Ім'я | Значення | Тип |
   |---|---|---|
   | `GOOGLE_CLIENT_ID` | Client ID з п. 5.2 | Text |
   | `GOOGLE_CLIENT_SECRET` | Client secret з п. 5.2 | **Secret** |
5. Зверху сторінки возьми адресу воркера: `https://fluxhelper-auth.<твій-субдомен>.workers.dev`
6. Додай `https://fluxhelper-auth.<твій-субдомен>.workers.dev/callback`
   у Authorized redirect URIs веб-клієнта (п. 5.2), якщо ще не додав.
7. Перевірка: відкрий `https://…workers.dev/` у браузері — має бути сторінка
   «FluxHelper Auth Bridge» з ім'ям клієнта.

Секрет у застосунку більше не потрібен для мобільного входу: він лежить
у змінній воркера, а в застосунок повертається зашифрований (AES-256-GCM)
одноразовий код, який живе 10 хвилин і міняється на токени тільки на сервері.

## 7. Крок 5 — зібрати і перевірити

1. Підстав `FH_WORKER_DEFAULT` в index.html (п. 4) — або задай дистанційно (п. 8).
2. Збірка `apk/build.sh` як завжди → підписи своїм ключем (SHA-1 не міняється).
3. **Тест на телефоні:**
   - «Увійти через Google» → вибір акаунта → системне віконце «Дозволити доступ»
     → профіль з'явився. (Це щойно ЗАПРАЦЮВАЛО після Java-патчу!)
   - Якщо системний шлях недоступний → «Увійти через браузер» → відкриється
     сторінка входу мосту → Google → автоматичне повернення в застосунок.
   - Перевір автовхід при наступному запуску (refresh через міст).
4. **Тест на ПК:** вхід має працювати точно як у 2.2.x–2.3.3 (код цього шляху
   не змінювався: той самий клієнт, секрет, loopback).

## 8. Крок 6 (опційно) — вмикати міст дистанційно

У Firebase RTDB `update/config.json` можна додати (без перезбірки APK):

```json
"oauth": {
  "worker": "https://fluxhelper-auth.твій-субдомен.workers.dev"
}
```

Застосунок підхопить URL сам і збереже локально. Це єдине поле, яке
застосунок приймає з дистанційної конфігурації — клієнти і секрети
дистанційно НЕ змінюються (захист від «поламаного конфігу», як у 2.3.1).

## 9. Чому це працюватиме, коли все інше падало

| Проблема минулих версій | Чому більше не актуальна |
|---|---|
| Google блокує OAuth у WebView (2.2.x) | вхід у ЗОВНІШНЬОМУ браузері; WebView більше не бере участі |
| «Custom URI scheme is not enabled» (2.3.0) | для мосту схема взагалі не реєструється в Google — Google бачить лише `https://…/callback`; для прямої схеми — виправлений package в Android-клієнті |
| MIUI вбиває процес і «вбиває localhost» (2.3.1–2.3.3) | loopback-сервер більше не потрібен: обмін коду робить Worker на сервері Cloudflare; повернення в застосунок — через deep link, який нічого не слухає |
| «запит додатка недійсний» (400) | PKCE тепер є всюди, де треба; секрет на телефоне більше не головний |
| Секрет у JS/дексі (безпека) | для мобільного входу секрет лишився тільки на Worker; у APK він залишається лише для ПК-шляху (там він і так був у exe) |
